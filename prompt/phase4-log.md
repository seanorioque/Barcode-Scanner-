# Phase 4 Execution Log — Barcode Capture

Running log of what actually happened during Phase 4. Unlike Phase 2 and 3, Phase 4 arrived as a single detailed working prompt (P1/P2/P3 issue list with a suggested commit sequence and Definition of Done) rather than a separate planning pass with its own `-plan.md` — this log is the only phase-4 artifact besides the diff itself. Newest entries at the bottom.

## 2026-08-15 — P1-1: orphaned photo files from abandoned scans

- `ScanRepository` gained `purgeOrphanedImages(Directory imagesDir)`; implemented in `SqliteScanRepository` by diffing every file in the directory against every `image_path` in the table (active and soft-deleted, no `WHERE` filter), and in `FakeScanRepository` as a no-op (nothing to purge in-memory).
- `ScannerController` gained `_deleteAbandonedImage(imagePath, duplicateImagePath)`, called from `rescan()` and the provider's `ref.onDispose` — the guard against the two cases explicitly, comparing against `state.duplicateOf?.imagePath` so a duplicate's already-saved photo is never touched.
- `main()` calls `SqliteScanRepository.purgeOrphanedImages` once, fire-and-forget (`unawaited`), after constructing the repository.
- New FR-30; bug-log entry #19.

## 2026-08-15 — P1-2/P1-3: unhandled database write failures

- `ScannerController.save` now catches any throw from `_repository.save`, resets `phase` back to `detected` (un-spins the Save button), and sets a new `ScannerState.saveError` field. `PreviewScreen` renders it as a plain SnackBar via `ref.listen`, then calls a new `dismissSaveError()` so it doesn't reappear on an unrelated rebuild.
- Same pattern (try/catch around the repository call, plain SnackBar, no exception text) added to: `ManualEntryScreen._save`, `EntriesScreen._editLabel`/`_deleteWithUndo`/`_deleteSelected` (including their Undo actions), and `RecentlyDeletedScreen._restore`/`_permanentlyDelete`.
- `SqliteScanRepository.save`'s `try/catch` now wraps both the `db.update` and `db.insert` branches (previously only the insert branch was guarded) — P1-3's premise held: the update branch can't currently throw a unique-constraint error since only labels are editable (ambiguity #11), but the guard is cheap insurance if that product decision ever changes.
- `FakeScanRepository` gained `throwOnSave`/`throwOnSoftDelete`/`throwOnRestore`/`throwOnPermanentlyDelete` flags and a `FakeDatabaseException` (a minimal `DatabaseException` subclass — `sqflite`'s public API only exports the abstract class, not the concrete `SqfliteDatabaseException`, so a small subclass was the cleanest way to construct one in tests without an `implementation_imports` lint warning).

## What turned out differently than the plan assumed

- **iOS and the Android debug build could not be verified end-to-end.** The plan's Definition of Done calls for `flutter build ios --no-codesign` and a clean `flutter build apk --debug`. This development machine is Windows (no Xcode/macOS toolchain — iOS was never buildable here) and severely memory-constrained (7.4GB total RAM; a Gradle daemon OOM-crashed earlier in this session, and even `flutter test` repeatedly strained available memory). Both fixes (P1-4, P1-5) were verified as far as this machine allows — inspecting the actual installed podspecs/gradle files rather than guessing at version numbers, `flutter analyze`/`flutter test` passing clean against the new dependency graph — but neither a real iOS build nor a real Android build has actually been run. This is a genuine, not cosmetic, gap: it should be the first thing verified on a capable machine (or in the new CI's `android-debug-build` job) before this is called fully done.
- **Test execution was much slower than expected** due to the same memory constraint — a `flutter test` run crashed the Dart VM with a native out-of-memory error on the first attempt, and a pile of orphaned `dart`/`flutter_tester`/`bash`/`tail` processes from earlier, unrelated sessions (some over a day old) had accumulated and were competing for the same scarce RAM. Cleaning those up (with the user's explicit go-ahead first) and reducing test concurrency to 1 were both necessary just to get a real pass/fail result, not code changes this plan anticipated needing.

## 2026-08-15 — Getting a real green test run: three genuine bugs, one environment dead end

Actually running the suite to completion (itself a struggle — see above) surfaced real problems, which is the entire point of running it. In order found:

- **Bug found in this phase's own code**: `ScannerController`'s `ref.onDispose` callback (added for P1-1's cleanup) read `state.imagePath`/`state.duplicateOf?.imagePath` directly. Riverpod 3.4.2 asserts `Cannot use Ref ... inside life-cycles/selectors` when a notifier's `state` getter is read from inside its own `onDispose` callback — this failed *every* test that disposed a `ScannerController` (most of `scanner_controller_test.dart`, `capture_screen_test.dart`, `preview_screen_test.dart`), cascading into ~30 failures that looked far scarier than the actual root cause. Fixed by mirroring `imagePath`/`duplicateOf?.imagePath` into two plain instance fields (`_imagePathForCleanup`/`_duplicateImagePathForCleanup`), updated by a new `_setState()` wrapper around every `state = ...` assignment in the controller, so `onDispose` reads the plain fields instead of going through `state`.
- **Bug found in this phase's own test code**: `test/widget/manual_entry_screen_test.dart`'s two new tests called `tester.enterText(...)` immediately followed by `tester.tap(... 'Save')` with no `pump()` between them. `ManualEntryScreen`'s Save button is conditionally enabled (`canSave = _valueController.text.trim().isNotEmpty && !_saving`), so the tap landed on a still-disabled button captured from the pre-text build — `_save()` never ran, and `repository.entries` stayed empty. `preview_screen_test.dart`'s equivalent pattern happens to work because *its* Save button is unconditionally enabled. Fixed by adding an explicit `await tester.pump()` after `enterText` in both new tests.
- **Pre-existing bug found, unrelated to this phase's diff**: `test/widget/recently_deleted_screen_test.dart`'s `lists deleted entries` test asserted `find.textContaining('Deleted')` finds exactly one widget — but `RecentlyDeletedScreen`'s AppBar title is literally "Recently Deleted", which also contains "Deleted", so this always matched two widgets. `git diff` confirmed neither the test nor the screen's title were touched this phase. This had simply never been caught, which is exactly the gap P2-5 (CI) exists to close — the working prompt's own framing ("the discipline depends entirely on remembering... two test runs were orphaned before finishing") turned out to be literally true of this exact test. Fixed by narrowing the finder to `'Deleted '` (trailing space), which only the relative-time subtitle has.
- **Environment dead end, ruled out rigorously, not fixed**: every test in `preview_screen_test.dart` and four `Dismissible`-swipe tests in `entries_screen_test.dart` intermittently failed/hung (the former hitting `pumpAndSettle`'s internal 10-minute timeout on literally every run). Given `ref.listen` was the only meaningful change to `PreviewScreen`, first suspected it and moved the save-error listener from `ref.listen` (re-registered every `build()`) to `ref.listenManual` in `initState()` (Riverpod's documented pattern for exactly this) — the hang persisted identically. Isolated further by temporarily restoring 100%-original (`git show HEAD:...`) `preview_screen.dart` and `scanner_controller.dart` and re-running the single failing test: **it still hung for the full 10 minutes on completely unmodified code**, proving this is a pre-existing environment fragility (this machine's severe, session-long resource exhaustion — see the OOM/thread-creation-failure entries above), not something this phase's diff caused. Restored my versions afterward (`listenManual` kept — it's still the more correct pattern even though it wasn't the fix). Not chased further; documented here rather than silently ignored.

Net effect: the suite is green except for `preview_screen_test.dart` and the four drag-gesture tests, which fail the same way on unmodified code under this machine's current load and should be re-verified on a healthier machine (or in CI) before being trusted either way.
