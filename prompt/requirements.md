# Functional Requirements — Barcode Capture

Extracted from `prompt/plan.md`'s `Section 1 (Functional)`, `Section 2 (Assumptions/decisions)`, `Section 5 (Screens)`, and `Section 6 (Edge cases)`. FR-01–FR-09 map to the IDs specified in the original brief; FR-10–FR-20 are additional requirements the brief describes but didn't number, or gaps closed during Phase 2. FR-21+ were added during Phase 3, when the app moved from "1D + QR" to **1D-only**, gained a photo capture/crop pipeline, a Recently Deleted trash, manual entry, search, and multi-select delete, and had several correctness bugs found and fixed. **That 1D-only narrowing was itself reversed on 2026-08-16 (ambiguity #23) — it was a real deviation from the brief, not a decision the brief left open. The app is back to 1D + QR.**

| ID | Requirement | Screen | Priority | Acceptance Criteria |
|---|---|---|---|---|
| FR-01 | List previously captured entries, most recent first | Captured entries | Must | Entries load ordered by `scanned_at DESC`. Each row shows value (monospace, ellipsis-truncated), a format chip, a relative timestamp, and a thumbnail of the cropped barcode photo when one exists (FR-23). List updates live (no manual refresh) via `StreamProvider` when an entry is saved, deleted, restored, or permanently removed. |
| FR-02 | Persist entries locally, surviving app restart | Data layer (all screens) | Must | Entries write to SQLite (`scan_entries` table: id, value, format, label, scanned_at, image_path, deleted_at). Force-quitting and relaunching shows all prior active entries unchanged. No network call occurs at any point (offline-only). |
| FR-03 | Start a new scan from the list screen | Captured entries → Capture | Must | A FAB (`Icons.qr_code_scanner`) is present on Captured entries (including empty state). Tapping it navigates to Capture and triggers the permission check (FR-13). |
| FR-04 | Detect 1D barcodes and QR codes via Google ML Kit | Capture | Must | Detector is scoped to exactly: EAN-13, EAN-8, UPC-A, UPC-E, Code 128, Code 39, Code 93, Codabar, ITF, and QR_CODE — other 2D formats (Data Matrix, Aztec, PDF417, ...) do not trigger a result. **Re-added QR 2026-08-16 after it was dropped during Phase 3 (see FR-21, ambiguity #23) — this now matches the original brief's "1D + QR" scope.** A steady, in-focus code of a supported format is detected in ~1s under normal indoor lighting. When multiple codes are in frame, exactly one is selected (largest/most central) via the documented pure-function selector, and that selection's bounding box is what FR-23's crop uses. |
| FR-05 | Give clear feedback the moment a code is detected | Capture | Must | On detection: haptic pulse fires, cutout border animates to the success color, frame analysis stops immediately, and navigation to Preview occurs ~300ms later (not instantly). State machine (`idle→scanning→resolving→detected→saving`) never pushes more than one Preview screen from repeated callbacks during the transition. The `resolving` phase exists specifically to let the duplicate check (FR-22) finish before Preview is shown, so Save is never briefly visible for what turns out to be a duplicate. |
| FR-06 | Show the detected value and its format on the preview screen | Preview & confirm | Must | Value renders in a selectable monospace block; format renders as a labelled chip; the cropped barcode photo (FR-23) renders above them when available. If the value already exists among active entries, the normal label/Save UI is replaced by the non-blocking "Already scanned" status described in FR-22 — this is no longer just an informational note next to an otherwise-normal Save flow. |
| FR-07 | Allow rescanning from preview without saving | Preview & confirm | Must | "Rescan" pops back to Capture and resets scanner state to `scanning`, with no confirmation dialog and no DB write. Detection resumes automatically, including when reached from the "Already scanned" state. |
| FR-08 | Save the entry from preview | Preview & confirm | Must | "Save" is reachable in one tap (label field doesn't autofocus) and is only shown for a non-duplicate detection (FR-22). Tapping it inserts a row (`id`=uuid v4, value, format, label-or-null, `scanned_at`=now UTC, `image_path`) and returns to Captured entries with the new row visible at the top. Save succeeds with an empty label. The controller also refuses to persist a detection flagged as a duplicate even if called directly, as a second line of defense behind the DB-level uniqueness constraint (FR-22). |
| FR-09 | Allow an optional user-supplied label on the entry | Preview & confirm | Should | Label field is present, does not autofocus, and is optional — save succeeds whether it's populated or blank. Applies to both scanned (FR-08) and manually-entered (FR-25) records. |
| FR-10 | Reveal absolute timestamp on tapping a row's relative timestamp | Captured entries | Could | Tapping a row's relative timestamp (e.g. "3d ago") displays the absolute date/time; tapping again reverts. Disabled while multi-select mode (FR-27) is active. |
| FR-11 | Show empty state with call-to-action when no entries exist | Captured entries | Should | When there are no active `scan_entries`, list is replaced by an illustration + "Scan your first barcode" CTA. Tapping the CTA navigates to Capture. Empty state disappears once ≥1 active entry exists. |
| FR-12 | Delete an entry via swipe, with undo | Captured entries | Should | Swiping a row asks for confirmation (a dialog: "Delete this scan?") before anything happens — **superseded from "delete immediately with undo" to "confirm, then soft-delete"**. On confirm, the entry moves to Recently Deleted (FR-24) rather than being removed outright, and a "Moved to Recently Deleted" snackbar with an "Undo" action appears for exactly 5 seconds (FR-29) — tapping Undo restores it (or reports failure if a same-value active entry now exists). If the snackbar times out unactioned, the deletion stands, but the row is still recoverable from Recently Deleted until the retention period elapses. |
| FR-13 | Request and handle camera permission states | Capture | Must | Permission is requested on entering Capture if not already granted. Denied → in-context explainer with retry (not a blank screen). Permanently denied → detected via `permission_handler` and routed to system settings. |
| FR-14 | Toggle torch during capture | Capture | Could | A torch control on the overlay toggles the device flashlight on/off. |
| FR-15 | Close capture without scanning | Capture | Must | A close control stops camera/analysis and returns to Captured entries with no entry created. |
| FR-16 | Show friendly error state when no camera is available | Capture | Should | If the device reports no camera, Capture shows a friendly error state instead of crashing; no preview/detection is attempted. |
| FR-17 | Suspend/resume camera on app backgrounding mid-capture | Capture | Should | On backgrounding, the camera controller disposes via `didChangeAppLifecycleState`; on resume it reinitializes and detection resumes, with no crash or frozen preview. **Note:** this covers OS-level backgrounding only — the separate in-app navigation case (returning to Capture from Preview) is FR-28. |
| FR-18 | Copy detected value to clipboard | Preview & confirm | Could | Tapping the value block copies the raw decoded value to the system clipboard. |
| FR-19 | Edit label on a previously saved entry | Captured entries | Should | Tapping an entry's label (or an edit affordance next to it) opens a small dialog pre-filled with the current label. Confirming persists the change via `ScanRepository.save`; leaving it blank clears the label back to `null`. Only the label is editable — the scanned value and format are immutable, since the value is now the app's unique identifier (FR-22). **Resolved 2026-08-15: tap-to-edit on the row, implemented in Phase 2.** |
| FR-20 | *(reserved — see Totals)* | — | — | FR-20 was assigned to label editing during Phase 2 drafting and then folded into FR-19 once implemented; kept reserved rather than reused, so historical references to "FR-20" (e.g. in commit messages) still resolve to label editing. |
| FR-21 | ~~Communicate "1D barcode scanner" throughout the UI, not "QR/2D scanner"~~ **Superseded 2026-08-16, see ambiguity #23** | Capture, Captured entries | Must | Originally: detector didn't accept QR, FAB/empty-state used a 1D-specific icon, and the scan guide was a wide horizontal rectangle. All reversed — QR is back in scope (FR-04), the FAB/empty-state icon is `Icons.qr_code_scanner`, and the guide is a square (frames a QR code correctly, still fits a 1D barcode) — see FR-03/FR-04. Kept as a record of what changed and why, per this doc's own convention of not renumbering or deleting superseded entries. |
| FR-22 | Block duplicate scans instead of creating a second record | Capture, Preview & confirm | Must | Before showing `detected`, the scanner looks up whether the value already exists among **active** (non-deleted) entries. If it does: no new row is created (enforced both in `ScannerController.save` and by a DB-level partial unique index on `value WHERE deleted_at IS NULL`); Preview shows a non-blocking, informational "Already scanned" banner (not an error/alert, no dismiss action required) with the existing entry's label (or "Add label" if none) and when it was first scanned; Save is replaced by "Done"; Rescan still works. A value that only matches a *soft-deleted* entry (FR-24) is **not** treated as a duplicate. The same rule applies to manual entry (FR-25). |
| FR-23 | Capture and save a cropped photo of the scanned barcode | Capture, Preview & confirm, Captured entries, Recently Deleted | Should | On a non-duplicate detection, a full-resolution photo is captured and cropped to the detected barcode's bounding box (mapped from the ML-Kit analysis frame onto the still photo via resolution-independent fractional coordinates, with rotation accounted for) plus ~25% padding on each side so the barcode isn't clipped. The crop replaces the saved image entirely (no full-frame photo is kept). If cropping fails for any reason (decode error, degenerate region), the uncropped photo is saved instead rather than a broken/empty image. The cropped photo displays with `BoxFit.contain` (not `cover`) everywhere it's shown, so a wide/short barcode crop is never re-cropped by a square thumbnail. A duplicate scan (FR-22) does **not** trigger a new capture — Preview shows the image already stored from the entry's first scan instead. |
| FR-24 | Recently Deleted (trash) with restore and permanent delete | Recently Deleted | Should | Deleting an entry (FR-12) sets `deleted_at` rather than removing the row. A "Recently Deleted" screen (reached from an AppBar action on Captured entries) lists soft-deleted entries most-recently-deleted-first, each with its value, format, photo thumbnail, and relative deletion time. "Restore" clears `deleted_at`, moving it back to active — blocked (with an explanatory snackbar) if an active entry with the same value already exists. "Delete permanently" (behind its own confirmation dialog, since it's irreversible) removes the row and its photo file from disk. Entries older than a configurable retention period (default 30 days) are purged automatically — including their photo file — whenever the trash is opened or the database is opened. |
| FR-25 | Add a barcode record manually, without scanning | Add manually | Should | An AppBar action on Captured entries opens a form: barcode value (required), format (dropdown of the same formats FR-04 supports), and an optional label. Saving applies the same duplicate rule as FR-22 (existing active value → inline "Already scanned" info, not saved, form stays open); a successful save returns to Captured entries with a confirmation snackbar. |
| FR-26 | Search Captured entries by value or label | Captured entries | Should | A persistent search field below the AppBar filters the active-entries list client-side, case-insensitively, by substring match against value or label. No matches shows a "No matches for …" message instead of an empty list. |
| FR-27 | Select and delete multiple entries at once | Captured entries | Should | Long-pressing a row enters selection mode: the AppBar switches to a close icon, a "N selected" title, and a delete action; each row gets a checkbox and tapping anywhere on it (row or checkbox) toggles selection; swipe-to-delete (FR-12) is disabled while selecting, so the gesture doesn't conflict with tap-to-select. "Delete" asks for confirmation (pluralized for >1 item), soft-deletes every selected entry, exits selection mode, and shows one "N items moved to Recently Deleted" snackbar whose Undo restores all of them together. |
| FR-28 | Reactivate the camera when returning to Capture via system/gesture back | Capture | Must | Rescan and Save/Done already leave the scanner correctly started or navigate past Capture entirely. A system/gesture back press from Preview does neither — it just pops back to Capture, which had its camera stopped for the capture/duplicate-resolution step (FR-22/23). Capture now detects this case (phase still `detected` after the Preview route closes) and calls `start()` again, so the live preview and detection resume automatically without requiring Rescan. Works repeatedly across multiple scan → back cycles. |
| FR-29 | Undo snackbar auto-dismisses after exactly 5 seconds | Captured entries | Should | Both the single-delete (FR-12) and multi-select-delete (FR-27) Undo snackbars use an explicit 5-second `duration`, not Material's ~4s default. Tapping Undo before it expires restores the entry/entries; letting it expire leaves the deletion in place (recoverable from Recently Deleted, FR-24, until the retention period elapses). A new deletion's snackbar replaces any still-showing one and starts its own 5-second timer. |

| FR-30 | Clean up orphaned scan photos | Capture, Data layer (all screens) | Must | A photo captured at detection time (FR-23) that's never saved — the user rescans, presses system/gesture back, or leaves Capture entirely before deciding — is deleted rather than left on disk indefinitely. Two layers: (1) immediate cleanup in `ScannerController.rescan()` and the controller's provider `onDispose`, which delete `state.imagePath` unless it's `null` or it's actually the path already on file for a duplicate entry (`state.duplicateOf?.imagePath` — deleting that would destroy a saved entry's image); (2) a startup backstop, `ScanRepository.purgeOrphanedImages`, which compares every file in `scan_images/` against every `image_path` in the table (active and soft-deleted) and deletes whatever isn't referenced, run fire-and-forget from `main()` so it never blocks first paint. |

## Totals

- **30 functional requirements** (9 explicitly numbered in the brief, 10 additional derived from the Screens/Decisions/Edge-cases sections during the initial requirements pass, FR-20 reserved/folded into FR-19 during Phase 2, FR-21–FR-29 added during Phase 3, and FR-30 added during Phase 4).
- **Screens covered:** Captured entries (FR-01, 02, 03, 10, 11, 12, 19, 21, 26, 27, 29), Capture (FR-03, 04, 05, 13, 14, 15, 16, 17, 21, 22, 23, 28, 30), Preview & confirm (FR-06, 07, 08, 09, 18, 22, 23), Recently Deleted (FR-24), Add manually (FR-25), Data layer (FR-30).

| 16 | **Bug found**: saving a new entry whose value collided with an unrelated *existing* active entry silently deleted that other entry | Root cause: `db.insert(..., ConflictAlgorithm.replace)` resolves conflicts on *any* unique constraint, not just the primary key — so the new partial unique index on `value` (added for FR-22) triggered a silent replace instead of the intended "block the save" behavior. | 18 | **Bug found**: permanently deleting an entry (or the 30-day retention sweep) removed the DB row but left its photo file on disk indefinitely | Fixed: both `permanentlyDelete` and the retention purge now also delete the associated file (best-effort — a failure to delete the file, e.g. already missing, doesn't fail the operation) | 2026-08-15 |

| 20 | **Bug found**: any repository write failure (disk-full, corruption, permissions) went uncaught, leaving the UI stuck | Root cause: `SqliteScanRepository.save` only caught unique-constraint `DatabaseException`s (on the insert branch — the update branch wasn't even guarded); nothing above it in `ScannerController.save`, `saveManualEntry`'s callers, the label-edit dialog, or the entries/Recently-Deleted delete-restore paths caught anything, so `ScannerController.save` left `phase` stuck at `saving` (Save button spinning forever) on any throw. ## Explicitly out of scope (unchanged from the original brief unless noted above)

Sync or backup, batch/continuous scanning, deep-link handling for URL payloads, landscape layout, tablet-specific layout. **No longer out of scope as of Phase 3**: search and filtering (FR-26) and delete-with-undo (already in scope, refined by FR-12/FR-24/FR-29).
